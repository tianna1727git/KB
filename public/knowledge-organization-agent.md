# Payo 知识整理 Agent：规则、字段和检索流程

版本：knowledge-organization-v2  
导出日期：2026-11-11  
适用范围：Payo Content Agent Studio 的新建知识整理任务、知识库检索及写作来源选择。

> 本文说明已实现的规则和边界，不是当前知识条目的数据导出。构建版本是否已上线，以发布结果为准。历史知识不会因代码升级自动重切或自动获得新字段。

## 1. 整体流程

资料上传或 URL 导入 → 转换 Markdown → 读取资料分类 → 按分类生成保留原文位置的证据块 → 提取知识与元数据 → 关联适用条件 → 核对证据、数字与冲突 → 人工选择保存 → 待审核知识 → 人工确认来源、知识及对外引用权限 → 检索与写作使用。

API 执行和人工任务包使用相同的分类上下文、字段与验证逻辑。资料中的文字仅作为证据，不作为 Agent 的操作指令。系统不因模型表示“完成”而跳过审核。

## 2. 七种分类的默认切分规则

| 资料分类 | 目标长度 | 最小语义单位 | 保留规则 |
| --- | --- | --- | --- |
| About Payoneer | 400–800 字符 | 独立主体/服务范围/团队职责主题 | 保留主体、服务对象、地区、职责边界和联系方式用途。 |
| Events | 600–1200 字符 | 活动议题或连续论点 | 区分活动信息、限时优惠、历史观点与常青方法；分别提取活动日期、政策有效期、统计年份。未知日期不得假定永久有效。 |
| Product Guide | 400–1000 字符 | 完整操作阶段及步骤 | 保留操作场景、产品、地区、平台、账户类型、前置条件、分支和步骤顺序。步骤编号只引用原文；不要混合不同版本或分支。 |
| Products & Solutions | 600–1200 字符 | 客户场景—需求—方案 | 提取产品名称、适用客户、业务场景、配套产品、资格、限制和价值依据。原文明示关系与建议关系必须区分。 |
| Product Brochure | 250–700 字符 | 产品卖点及限定条件 | 功能、宣传卖点必须与资格、地区、费率、有效期及脚注一起保存；不得将优势改写成保证。 |
| Templates & Tools | 400–1200 字符 | 工作表或计算模块 | 保留输入、输出、单位、公式和参数依据。没有原公式时明确标记未保留公式；Markdown 表格不代表可执行计算器。 |
| Whitepaper | 800–1500 字符 | 研究问题、结论及证据 | 保留研究主题、国家/行业、发布年份、统计期间、样本口径、数据来源及局限。历史数据不改写为当前事实。产品关联只能是有证据的建议。 |

长度指 JavaScript 字符数，是语义分组目标，并非硬性截断。优先章节、段落、表格和代码边界；不足目标长度的完整主题不强行填充。单个证据块上限 3,500 字符，超大表格或连续段落可能被拆成带 continued 标记的连续块，必须结合邻接块核对。各块拼接必须与原文完全一致。

每批最多 3 个证据块、35 个提取条目；整份最多 200 个条目，正文最多 16 万字符。超限需拆分资料，不能静默忽略后文。API 与任务包还有结果大小限制；过大结果会报错，不视作成功。

只有网页链接、未转写视频入口或缺少正文的图片资料不能直接作为已整理知识。需要先抓取网页正文、OCR 或语音转写。Markdown 化的 Excel 如未保留公式，不具备原计算器的可执行性。

## 3. 字段约定

### 3.1 来源与证据

| 字段 | 含义 |
| --- | --- |
| policyVersion | 整理规则版本 |
| libraryCategory / sourceFormat | 整理时的资料分类快照、源文件格式 |
| sourceId / sourceFamilyId / sourceVersion / sourceHash | 原始资料身份、来源族、版本及内容指纹 |
| evidence | 逐字引文、证据块 ID、原文起止位置 |
| sourceLocations | 引用块的标题路径、父章节标识、前后块及续接标记 |
| sourceSegments | 文档级证据块目录；不在每个切片重复存整份正文 |
| sourceItemId | 整理结果中的稳定条目标识，用于关联条件和前后步骤 |

资料分类元数据修改不改原文版本。已有切片保留整理时的分类快照；修改资料分类后，需要重新整理才能应用另一类切分规则。

### 3.2 每个条目的 organization

| 字段 | 类型与规则 |
| --- | --- |
| scenario | 操作/客户场景名称；作为待确认的检索分组建议 |
| process | 流程名称；不能凭空补造步骤 |
| stepNumbers | 原文明确的第 N 步或编号列表；整数数组；不将整理顺序冒充原文步骤 |
| branch | 分支条件；必须逐字出现在本条证据中 |
| prerequisites / conditions | 前置条件与适用限制；必须逐字引用 |
| dates | kind、value 数组；value 保留原文表达并有当前引文支持 |
| contentRole | evergreen、event_info、promotion、historical 或 unknown |
| researchTopic | 研究主题；作为待确认的检索关联建议 |
| toolInputs / toolOutputs / formulas | 工具输入、输出、公式；逐字引用，无依据则为空 |
| relationshipBasis | suggested：场景、流程、研究主题分组为关联建议 |
| organizationWarnings | 缺失时间、公式、流程元数据或兼容旧结果等人工检查提示 |

新 API 任务要求结构化 organization。人工导入兼容旧结果格式，但会记录缺失元数据警告，不能声称具有完整流程/时效信息。前置条件、分支、公式、日期或步骤编号与证据不符时拒绝导入。

### 3.3 产品、场景及跨分类关联

产品实体 productEntities 分为 registered 与 candidate。已注册产品使用统一 ID，中英文别名归一；未知产品词只有证据支持时才保留为候选，不自动合并进产品注册表。

| 产品标识 | 标准名 | 当前别名 |
| --- | --- | --- |
| product:payoneer-card | Payoneer 随心付 | 随心付、payoneer card、payoneer cards |
| product:receiving-account | Payoneer 收款账户 | 收款账户、receiving account、receiving accounts、本地收款账户、全球swift、swift收款 |
| product:checkout | Payoneer Checkout | checkout、派安盈收单、payoneer收单 |
| product:payment-request | Payoneer 收款请求 | 收款请求、request a payment、payment request |
| product:fx | 派安盈换汇 | 预约汇率、余额互换、换汇、currency conversion |
| product:working-capital | Payoneer 营运资金 | early payments、working capital、速盈收 |
| product:vmp | VMP 全球生态聚合平台 | vmp、全球生态聚合平台、全球生态聚集平台 |

产品识别依据条目引文及其引用块的标题路径。Products & Solutions、Product Brochure、Product Guide、Templates & Tools 和 Whitepaper 均可共享这些 ID；关联不代表适用地区、政策版本或数值口径相同。

scenarioId 结合注册产品、平台、地区和场景名生成；researchTopicId 根据主题名生成。相同措辞才可直接共享标识，近义场景不会被无证据强行合并。未来产品与别名需要显式维护注册表；当前不提供自动词表治理后台。

## 4. Product Guide 的步骤连续性

流程同时保留 processFamilyId、processVersionId 与 branch。流程族以来源族和流程名区分，流程版本包含来源内容指纹；不同版本不能合成一套步骤。

flow 保存 originalStepNumbers、sequenceOrder、previousSourceItemId、nextSourceItemId 和 knownStepCount。sequenceOrder 明确标为“整理序号，非原文步骤编号”。前后关联限定于同一流程版本、同一分支。

文档另存 processOverviews，列出已保存步骤及原文编号。如果看到原文第 1、3 步，会标出编号 2 的断点；连续编号也不等于确认覆盖全部原文。不会从第一个观察到的编号推断缺失前文，也不猜测最后还有几步。

例：用户搜索“随心付”，检索结果可召回同产品的产品介绍、宣传页和指南。命中指南第 3 步后，一跳补齐同版本流程片段；详情显示原文步骤、分支、流程目录及相邻原文。不同账户类型的分支分别展示，不串成单一操作链。

## 5. Events 与其他资料的时效规则

日期种类：published（发布时间）、event_start / event_end（活动时间）、effective / expires（政策生效/到期）、data_period（数据统计期）。活动日期、政策期限和统计期不可互相替代。

- 常青方法 evergreen：活动结束不使其自动失效；仍保留来源和适用条件。
- 活动信息 event_info：有明确活动结束日时据此判断过期。
- 限时优惠 promotion：需要明确政策到期日；不会用活动结束日替代优惠期限。
- 历史数据 historical：保留历史标记与统计口径，不改写为当前事实。
- 未知 unknown：保留未知，不补造日期或有效期。

自动时效比较仅接受能够验证的完整年月日，如 2026-11-11 或 2026年11月11日；只有年份、相对日期或复杂日期范围时保留原文，需人工确认。日期按 UTC 判断，到期日保留至当天结束。

尚未生效、已到期的条目不进入写作可引用来源。活动/优惠缺少明确期限时，须先人工确认来源到期设置；这属于人工确认，不会回填或改写原文日期。知识库仍允许查看历史资料并显示提示。“未发现过期标记”不等于内容已经独立核验或永久有效。

## 6. 关键词检索流程

目标是对当前用户有权访问的知识进行完整候选召回，不因资料分类或固定 Top K 丢掉后续候选；“所有相关”指当前规则能识别的相关内容，不承诺语义层面的绝对穷尽。

1. 关键词做 NFKC、大小写及空白归一。
2. 按维护的产品、地区、平台别名扩展，例如“随心付”与“Payoneer Card”。明确文件名查询优先按完整文件名匹配，避免泛品牌扩展淹没结果。
3. 在标题、正文、产品/平台/地区/关键词、场景和研究主题中召回；匹配来源文档时，其其他切片作为来源上下文。
4. 从直接命中项进行一跳关联：同一流程版本、同场景、同研究主题、原文支持的关联条件、相邻步骤。
5. 查询能识别到注册产品时，跨七类召回共享产品标识的切片；不把共同词出现解释为事实等价。
6. 排序优先直接命中，再显示关联上下文，分别统计数量并显示匹配原因、版本和时效。
7. 分页浏览完整候选；知识库每页最多 50 条，搜索接口每批最多 100 条；写作候选每批 60 条，可继续加载。

当前实现是关键词/别名、实体标识与一跳关联，不是向量检索或任意语义推理。未在词表中的缩写、近义词和只有隐含语义的关系可能漏召回；候选包含关联上下文，因此也可能存在需人工排除的宽泛结果。默认跨分类，用户主动设置的状态、类型或来源过滤会限制搜索范围。

## 7. 检索、阅读与写作的边界

知识库可以显示待审核与历史内容；写作仅使用当前用户已确认、来源有效且允许对外引用的条目，继续执行来源版本一致性检查。被排除条目不参与知识库结果。

切片详情补充同流程版本的步骤目录、父章节及相邻原文；原文补充预算为 24,000 字符，超过时明确标为截断，不将节选冒充全文。

写作候选无前 60 条的总数截断；前端逐批加载。单篇文章仍最多选择 20 条证据，并在确认时重新校验知识版本、来源版本和权限。自动研究路径采用有限主证据与上下文，避免将所有候选直接送入模型。完整召回与模型上下文预算是两层机制。

所有读取按用户所有者隔离；关联扩展不能越过所有权、来源有效性或引用权限。

## 8. 升级与兼容

新建整理任务使用 v2；正在进行的旧任务和旧人工任务包保留兼容，不自动覆盖旧知识。已生成的历史任务如被系统复用，不会仅因升级代码重新执行。

已有知识缺少新元数据时仍可按原文字段检索，但流程、产品和时间关联可能不完整。若要全面应用新规则，需要单独安排历史资料重新整理及人工审核；本次更新不自动触发付费模型批量处理。

只修改规则和检索逻辑，不修改数据库绑定、用户访问范围、API 凭据或来源原文。新字段保存在现有记录负载中，无需新增数据库表。

## 9. 验证方式

自动化验证覆盖：七类证据块无损拼接、结构化输出约束、伪造步骤/日期/条件/公式拒绝、产品别名标识、流程版本与分支、步骤断点、事件时效、超过百条的完整分页、分类覆盖进入真实任务包、证据导入到数据库、人工待审核状态、权限隔离、写作候选超过 60 条继续选择及历史功能回归。

模型请求使用模拟响应；测试不触发线上付费整理。生产发布由 Sites 部署结果单独确认。
